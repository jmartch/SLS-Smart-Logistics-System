## Diagnóstico actual

El frontend ya cuenta con router, sesión autenticada, shell privado y navegación por permisos. Registro, listado y detalle de paquetes consumen la API real; listado y detalle de rutas también fueron integrados y el portal legado dejó de estar activo en la navegación. La pantalla `PlanningPage` continúa usando `PACKAGES` de `mockData.ts` y simula la planificación con un temporizador.

El backend expone y protege `POST /api/v1/routes/planning/plan-and-assign`, pero el frontend no puede construir todavía una solicitud operativa sin inventar identificadores: el contrato exige `depotId`, `vehicleIds` y `courierIds`, mientras que no existen endpoints de lectura para depósitos y los controladores de vehículos y mensajeros solo permiten creación. Además, el caso de uso actual siempre crea rutas nuevas: una ruta `PLANNED` o `READY` que se cruza con la ventana bloquea sus recursos y no puede recibir paquetes adicionales. El flujo de UI acordado debe iniciar la planificación por acción del coordinador, generar una propuesta automática y permitir seleccionar explícitamente una ruta `PLANNED` editable para recalcularla; una ruta `READY` mantiene su manifiesto congelado.

## Paso actual

### Paso 6 — Catálogo de recursos para planificación

**Por qué:** `PlanningPage` no debe enviar identificadores codificados ni confiar en datos simulados. El backend debe ofrecer al coordinador los depósitos, vehículos y mensajeros del tenant que puede seleccionar para una ventana de planificación.

**Debe aplicar el equipo backend propietario de planificación/recursos:**

1. Definir un contrato de lectura tenant-scoped para recursos de planificación, sin exponer modelos Prisma.
2. Incluir depósitos, vehículos/mensajeros elegibles y rutas `PLANNED` editables con capacidad restante; documentar cómo influye la ventana horaria.
3. Proteger la lectura con autenticación y `COORDINATE_ROUTES`.
4. Probar aislamiento por tenant y exclusión de recursos ajenos o inactivos.

**Archivos esperados:**

- `backend/src/modules/route-planning/application/`
- `backend/src/modules/route-planning/infrastructure/`
- `backend/src/modules/route-planning/presentation/`
- `backend/src/modules/route-planning/test/`

**Lote mecánico disponible para Codex:** ninguno hasta que el contrato público y la política de elegibilidad sean definidos por el equipo.

**Verificación:**

```text
docker compose exec backend npm test -- --runInBand <tests-del-catalogo>
docker compose exec backend npm run build
```

Comprobar además que el tenant A no recibe depósitos, vehículos o mensajeros del tenant B.

**Criterio de salida:** el frontend puede obtener todos los identificadores requeridos por `plan-and-assign` desde una API autorizada y tenant-scoped, sin constantes de demostración.
