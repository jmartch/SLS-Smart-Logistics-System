## Diagnóstico actual

El frontend ya cuenta con router, sesión autenticada, shell privado y navegación por permisos. Registro, listado, detalle y clasificación de paquetes consumen la API real; planificación, pendientes, listado y detalle de rutas también fueron integrados localmente y el portal legado dejó de estar activo en la navegación. Los cambios de planificación aún no tienen commit ni una prueba end-to-end sobre datos persistidos.

El backend expone y protege el workspace, la planificación automática iniciada por el coordinador y la replanificación explícita de una ruta `PLANNED`. El frontend obtiene `depotId`, `datasetId`, vehículos y mensajeros desde el workspace real; una ruta `READY` mantiene su manifiesto congelado. Falta demostrar el flujo completo con persistencia real y cubrir los nuevos clientes/pantallas con pruebas enfocadas.

## Paso actual

### Paso 6 — Validar planificación y recuperación manual de extremo a extremo (Bloque 5)

**Estado de implementación:** El backend expone el workspace, `plan-and-assign` y la replanificación de rutas `PLANNED`; `PlanningPage`, `PendingAssignmentsPage` y `RouteDetailPage` consumen esas APIs sin `mockData.ts`. La suite completa del backend (148 suites, 1274 pruebas), la suite del frontend (6 archivos, 32 pruebas), ambos builds y el lint frontend con 0 errores pasan. Durante la auditoría se corrigió un objeto `CapacityClusterProposal` incompatible que impedía compilar el backend.

**Revalidación 2026-10-13:** 155 suites/1362 pruebas backend y 10 archivos/70 pruebas frontend aprobadas; ambos builds pasan. No se repitió lint ni integración persistente. Mi ruta y las acciones iniciar/interrumpir ya están conectadas. La consulta autenticada del workspace devuelve dos candidatos sin coordenadas listas y cero vehículos/mensajeros elegibles; los tres paquetes OSM ya están asignados. Preparar el escenario de ensayo sigue pendiente. Ver [auditoría DEMO-01](../demo/demo-01-report.md).

**Actualización de semillas y prueba integrada 2026-10-13:** El usuario autorizó la limpieza global y la modificación de semillas. El nuevo `test:demo-01` verifica por HTTP/PostGIS el recorrido de clasificación, planificación, pendiente, recuperación, preparación y bloqueo de edición (3 escenarios aprobados). Las semillas dejan tres paquetes REGISTERED con coordenadas válidas y una pareja libre. El entorno local se reinició y el worker procesó los tres eventos nuevos. Falta el ensayo visual y la suite específica del cliente planningApi; ver [runbook](../demo/mvp-demo.md).

**Pendiente original, cubierto ahora por test:demo-01:** Añadir una verificación integrada reproducible que cubra `CLASSIFIED` → planificación manual → ruta `PLANNED`, recuperación de un `PENDING_ASSIGNMENT` sobre esa ruta, preparación a `READY` y rechazo posterior de replanificación. Debe comprobar persistencia de asignación/historial, aislamiento por tenant y eventos Outbox. Después, añadir pruebas de contrato del cliente frontend para workspace, planificación, replanificación y acciones de ruta.

**Archivos esperados:** extender `backend/test/assignment-planning.e2e-spec.ts` y `backend/test/integration/assign-01.cjs` para el flujo persistente; crear `frontend/src/app/planificacion/planningApi.spec.ts` y ampliar `frontend/src/app/rutas/routesApi.spec.ts` para los contratos HTTP. No usar la base compartida: `test:assign-01` requiere `GDB_TEST_ADMIN_URL` de un PostgreSQL/PostGIS desechable.

**Verificación:** `docker compose exec backend npm run test:assign-01`, `docker compose exec frontend npm test`, `docker compose exec backend npm run build` y `docker compose exec frontend npm run build`. El criterio de salida es demostrar aislamiento por tenant, una sola asignación activa por paquete, historial y Outbox coherentes, y que una ruta `READY` rechaza replanificación.

## Decisiones

| Fecha | Decisión | Motivo | Consecuencia |
| --- | --- | --- | --- |
| 2026-09-28 | Organizar el frontend alrededor de tareas por rol | Reduce pantallas genéricas y sigue los módulos del dominio | Paquetes, planificación, rutas y administración son features independientes |
| 2026-09-28 | Usar detalle con pestañas y acciones en diálogos cuando no necesitan URL propia | Mantiene pequeño el mapa de rutas del MVP | Historiales, evidencia y reasignación no se convierten automáticamente en páginas |
| 2026-09-28 | Mantener contratos simulados solo como herramienta temporal | El backend actual aún no expone las APIs necesarias | Ningún módulo UI puede quedar `DONE` hasta integrarse con la API real |
| 2026-09-28 | Tratar el dashboard analítico como opcional | `AGENTS.md` lo deja fuera del núcleo obligatorio | La portada privada inicial será una bandeja de trabajo simple |
| 2026-10-12 | La planificación es iniciada manualmente y produce una propuesta automática | El coordinador debe decidir cuándo planificar y revisar el resultado antes de preparar | No ejecutar planificación continua ni modificar rutas existentes silenciosamente |
| 2026-10-12 | Solo una ruta `PLANNED` puede seleccionarse para recalcular/agregar paquetes | El manifiesto se congela al pasar a `READY` | La reutilización de ruta requiere un caso de uso explícito; `READY` y estados posteriores no son editables |
