# GDB-04 — Calendario, ventanas y disponibilidad

Estado: fase de esquema y persistencia terminada; migraciones GDB-04 e integridad adicional probadas y aplicadas a SLS. Integración funcional de planificación pendiente.

La migración `20260915040000_calendar_windows_availability` añade Depot, DeliveryWindow, VehicleShift, CourierShift y PlanningPackageResult. Añade campos de calendario a Package, RoutePlanningRequest, Route y RouteStop. Los instantes nuevos usan `timestamptz(3)`; los timestamps históricos no se convierten. Las columnas nuevas en tablas existentes son nullable para conservar filas anteriores sin inventar duración, ventana o turno.

Restricciones SQL: intervalos de ventanas y turnos positivos; turnos del mismo recurso sin solapamiento mediante GiST y `btree_gist`; duración de servicio positiva; orden básico de tiempos planificados; totales no negativos; una ruta no cancelada por vehículo y fecha de servicio. Las FK compuestas protegen la pertenencia al tenant de depósito, ventana, recurso y geocodificación. El dataset de la solicitud tiene FK a GeoDataset.

Antes de aplicar a SLS: respaldar la base, confirmar `migrate status`, contar filas de Package, RoutePlanningRequest, Route y RouteStop, e inspeccionar duplicados de `(tenantId, vehicleId, serviceDate)` para rutas no canceladas si alguna fecha se pobló por otro despliegue. Confirmar que el rol de migración puede instalar `btree_gist`. La migración se ejecuta dentro de `BEGIN/COMMIT`, por lo que una restricción fallida revierte todo el bloque. Probar primero con copia aislada de esquema y datos representativos; no usar `migrate reset` en SLS.

Después detuvo el backend y ejecutó `prisma migrate deploy` desde un contenedor puntual: Prisma informó que aplicó `20260915040000_calendar_windows_availability` y que todas las migraciones se aplicaron correctamente. Un segundo contenedor ejecutó `prisma migrate status` y respondió `Database schema is up to date!`. Persistencia no equivale a planificación funcional. El caso de uso todavía debe exigir servicio completo dentro de la ventana y deadline, esperar si llega temprano, verificar regreso dentro de los turnos, capacidad tras cada inserción y motivo para cada paquete pendiente. También debe verificar que ventana y geocodificación de RouteStop correspondan al paquete asignado; las FK actuales solo prueban tenant. Los metadatos de algoritmo, dataset, zona horaria y horizonte quedan nullable para compatibilidad; el nuevo planificador debe exigirlos y fijar su versión antes de crear rutas.

## Integridad adicional de base de datos

La migración nueva `20260915041000_calendar_integrity` exige `reasonCode` no vacío para resultados `PENDING`. Un trigger valida que una parada con `deliveryWindowId` tenga inicio y fin de servicio y que el servicio completo quede dentro de la ventana elegida. El trigger de DeliveryWindow impide que una edición posterior de horarios o paquete invalide paradas que la referencian. La lectura de la ventana usa lock `FOR SHARE` para sincronizar con actualizaciones de esa fila. Ninguna de estas reglas sustituye la selección funcional de ventanas, el deadline, los turnos o la capacidad.

Antes del despliegue adicional se comprobó directamente desde Docker que SLS tenía cero PlanningPackageResult y cero RouteStop con ventana elegida. Prisma mostró ocho migraciones y solo `20260915041000_calendar_integrity` pendiente. Se creó `/tmp/sls-before-gdb04-integrity.dump` (170 KB), y `pg_restore -l` pudo leer sus 430 entradas. La migración pasó primero en `sls-gdb04-test` (BEGIN/COMMIT) y `backend/test/sql/gdb-04-integrity.sql` devolvió siete PASS, DO y ROLLBACK. Luego se detuvo el backend, Prisma aplicó la migración a SLS, y la misma prueba SQL devolvió siete PASS y ROLLBACK en SLS. `migrate status` informó `Database schema is up to date!`. El backend se reinició, Nest compiló con cero errores y respondió `Hello World!` desde dentro de `sls-backend`. La conexión HTTP desde el shell aislado del asistente a localhost:3000 no estuvo disponible; la comprobación interna del contenedor sí pasó.

Verificación local: `prisma validate` y chequeo TypeScript sin emisión pasaron. `npm run build` no pudo limpiar un artefacto `backend/dist` por permisos. Docker no estaba accesible para el asistente. El usuario ejecutó `backend/test/sql/gdb-04-calendar.sql` en `sls-gdb04-test` y compartió primero nueve y luego catorce avisos PASS, `DO` y `ROLLBACK`. La segunda ejecución cubrió duración, ventanas alternativas, intervalo inválido, aislamiento de tenant, turnos adyacentes y solapados, horizonte invertido, resultado único por solicitud/paquete, espera temprana, orden de tiempos de servicio, unicidad vehículo/día y excepción de ruta cancelada. Esto demuestra esas reglas en PostgreSQL temporal; no incluye salida independiente de aplicación de la migración ni prueba funcional del planificador.
